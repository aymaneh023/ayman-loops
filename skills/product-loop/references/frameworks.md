# Frameworks

The methods each step uses. Sources are named so a reader can check them.

## Opportunity tree (Teresa Torres, *Continuous Discovery Habits*)

Goal → opportunities → options → tests. An **opportunity** is a problem or need in the words of the person who has it ("I don't know whether my child practises enough"), never a feature ("a parent dashboard"). A request for a feature is one option under the opportunity behind it. Several items can support one opportunity; one item can support several.

## Confidence (after Itamar Gilad's Confidence Meter)

Confidence says how strong the evidence is, 0–10. Approximate levels from Gilad's published examples:

| Evidence | Confidence |
|---|---|
| An opinion or idea, a trend | ≈ 0.1 |
| One or two mentions, anecdotes, one request | ≈ 0.5 |
| Market data, buyer signals, a survey | ≈ 1–1.5 |
| Several interviews pointing the same way | ≈ 2.5–3 |
| Usage data, results of a real test | ≈ 6+ |

Count items by type and by distinct speaker: five quotes from one person are one person. Contradicting items lower confidence; say how.

## ICE

Impact × Confidence × Ease, each 1–10, used to rank options. Impact: how much the option moves the goal in the context pack if it works. Confidence: the level above, rounded up to at least 1. Ease: the loop's guess, confirmed or changed by the user at checkpoint 1. Until the user confirms Ease, rank by Impact × Confidence and say so.

## MoSCoW

Must, Should, Could, Won't (this time). The loop proposes it; the user confirms or changes it at checkpoint 1. When most items end up Must, point that out: the usual failure of MoSCoW is too many Musts.

## The four risks (Marty Cagan, SVPG)

Every option rests on assumptions about **value** (will they want it?), **usability** (can they use it?), **feasibility** (can we build it?) and **viability** (does it work for the business: sales, cost, privacy, the buyer?). Name the riskiest one; the cheapest test targets it.

## Cheapest test

Cheapest first: look at data we have → ask five people → a fake door or a hand-made version (send the e-mail by hand) → a prototype → a real build. A test card says: the assumption, the test, the result that would change the plan, who runs it.

## PR-FAQ (Amazon, *Working Backwards*)

For a proposal the user marks as a **bet**. Before any PRD change:
- **Press release**, one page, written as if it has launched: headline, who it is for, the problem, the solution, a quote from a customer, how to start.
- **External FAQ**: questions a customer would ask.
- **Internal FAQ**: questions the team asks: cost, risks, why now, what we will not do.

If the press release does not convince the user, the bet goes back to Explore.

## Journey (Nielsen Norman Group)

Per segment: the moments in order (left to right), what the person does, thinks and feels at each, and where it hurts. Each pain point cites its items. Update a journey by adding or changing moments, never by redrawing it from scratch; keep the top-level moments stable.
